# DBT Code Cache Sweep Design

> Issue: [#498](https://github.com/CertifiedBadIdeas/Compukter-Kraft/issues/498)

## Goal

Measure how the persistent per-VM DBT code-cache capacity affects the optimized C workload relative to native Clang and QEMU TCG.

## Design

Keep `max_instructions` fixed at 8 and cache metadata fixed at 32 sets. Separate the 8 KiB one-block translation workspace and bounded scratch from persistent cache storage so changing cache capacity does not change unrelated memory. Sweep persistent cache capacities of 16, 32, 64, 128, 256, and 512 KiB in the existing 21-sample C/QEMU harness.

Each row reports normalized execution time, native/QEMU ratios, hits, misses, metadata evictions, overlap invalidations, translations, generated bytes, reserved bytes, and steady-state allocations. Native and QEMU are measured once in the same rotating run.

## Invariants

- The guest workload, checksum, compiler flags, cache sets, block limit, ABI, and instruction-budget semantics remain unchanged.
- Direct DBT remains available and uses an 8 KiB scratch.
- Timed product execution remains allocation-free.
- This slice selects a cache-capacity experiment; it does not change the default backend or block size.
